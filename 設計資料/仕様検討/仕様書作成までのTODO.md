## A. 仕様確定が必要な未決事項

仕様書を書く前に意思決定が必要な項目。決定なしに設計書は書けない。

### A-1. 対応表作成手法のリスト確定【重要度：高】【状態：議論中（打ち合わせ予定）】
- ヒト対非モデル生物ではオルソログ対応表が存在しないのが通常であり、対応表の作成手法の選択肢整理が必須。
- **PoCで確認された実績手法：**
  - fanflow（坊農先生）：複数種への一括対応表生成（ミツバチ対応表`functional_annotation_transcript_Ac.tsv`はこの出力）
  - tblastn：対応表にない遺伝子の補完に使用。**リファレンスがヌクレオチド配列（TSA等）の場合はblastpでなくtblastnが必要。** リファレンス種別（タンパク質fasta vs ヌクレオチドfasta）によって手法が変わる。
  - blastp：リファレンスがタンパク質fastaの場合の補完手法（初期手順）
- **現在判明している候補：** DIAMOND（RBH+）、fanflow、tblastn/blastp（補完用）。他にもプロジェクトにより選択したい手法がある可能性。
- **判断が必要な問い：** サポートする作成手法のリストを確定し、統一入力フォーマットへの変換方法を決める。手法を仕様書で抽象化するか、参照実装（DIAMOND等）を明示するか。
- **近日打ち合わせで議論予定。**
- 影響範囲：Level 1 Context図・Level 3 Component設計・A-4（統一フォーマット定義）・パラメータ定義（閾値等）

### A-2. 手動介入範囲の確定【重要度：高】【状態：議論中】
- 叩き台では「BLASTpヒット後の機能確認のみ手動」としているが、ノード書き換え（XML編集）も手動になる可能性があるという指摘がある。
- **PoCで確認された手動介入の具体的な形態（カイコ実績より）：**
  1. **パラログ統一の判断：** 複数の遺伝子シンボル（例：LDHA/LDHC/LDHAL6B）が同一カイコ遺伝子にマップされる場合、どれを正とするかの選択。
  2. **no hit対応：** tblastnでもヒットなし（例：NAGS・GATM・GAMT）の遺伝子への対応方針の決定。
  3. **blast結果の機能確認：** ヒットした配列がヒトのものと同様の機能を持つか確認。
  4. **1:N対応の選択：** 複数ヒットがある場合の最適候補選択（例：PCK1に7ヒット）。
  - ノード書き換え（PathVisio等での編集）は現状手動。自動化可否は未確認（B-2参照）。
- **ツールが担うべき役割：** 上記手動判断が必要な遺伝子をリストアップして研究者に提示する。結果の記録・理由の記載欄を提供する。
- **判断が必要な問い：** ノード書き換えは自動化できるか？バイトスタッフへの確認が必要。
- 影響範囲：Level 2 Containerのモジュール③・Level 3の分岐ポイント・全体の自動/手動の境界線【A-8と連動】

### A-3. 研究者の責務範囲【重要度：高】【状態：決定済み：ファイル選択は研究者責務、必要なファイル種別の案内はシステム責務】
- **確定した方針：**
  - **研究者の責務：** 具体的にどのファイルを使うかの決定。既存の遺伝子対応表など研究者の知見に基づいて選択される部分であり、機械的なURL生成などで自動化が難しい。
  - **システムの責務：** どのタイプのファイルが必要かを研究者がわかるようにサポートすること。設定ファイルの設計を通じて「何を入力すれば良いか」を明示し、入力に迷わないよう工夫する。
- **設計への含意：**
  - Level 1 Contextの「研究者」ノードは「必要なファイルを判断・選択・提供する」役割として定義する。
  - ツールは入力ファイルの種別をバリデーションし、不足・不整合があればわかりやすいエラーや説明を返す。
  - 設定ファイルにはコメントや説明を充実させ、研究者が迷わず入力できるUI（CLI/設定ファイルの設計）を目指す。
- **A-6との連動：** 設定ファイルの具体的な項目設計（何をどう記述させるか）はA-6で決める。
- 影響範囲：Level 1 Context図・入力パラメータの定義・設定ファイル設計（A-6）・バリデーション設計

### A-4. オルソログ変換テーブルの構造定義【重要度：高】【状態：議論中（設計前提の見直しが必要）】
- 本ツールの必須前提条件であるオルソログ変換テーブル（ヒト→対象種の遺伝子ID対応表）が、どのような属性・キー構造を持つべきかが未定義。
- **PoCで判明した事実：設計前提との不一致。**
  - 設計は「RefSeqタンパク質ID（NP_xxx）とEntrez Gene IDの両方を保証する列構成」を前提としていた。
  - 実際のテーブル（ミツバチ・カイコ）はヒト側がEnsembl protein ID（ENSP*）、対象種側がプロジェクト固有ID（MSTRG*/KWMTBOMO*）であり、RefSeq NP_xxxはどこにも登場しない。Entrez Gene IDも表内になく、別途NIH protein検索で変換する。
  - 対象種のIDは論文・プロジェクトごとに異なる（標準化されていない）ことが実態であり、テーブルの「列構成を固定する」という設計の立て方自体を再考する必要がある。
- **設計問いの再定義：** 「テーブルが持つべき列構成」ではなく「パイプラインが受け入れられるID体系の種類と変換ステップ」として設計する。
- **判断が必要な問い：**
  - どの粒度で対応を持つか（遺伝子レベル／転写産物レベル等）
  - テーブルに載らない遺伝子（IDマッピングが存在しないもの）はどう区別して管理するか
  - 研究者がどのID体系を使っているかをどうツールに伝えるか（A-6の設定ファイルで定義？）
- 影響範囲：Level 3のパラメータ定義・スキーマ設計・入力バリデーション設計・A-6（設定ファイル仕様）・A-8（変換フロー分岐ダイアグラム）
- ※他の未決事項（A-1の手法選択・A-5の代替フロー）に先行して定義が必要。

### A-5. 入力ファイルと責務の対応整理【重要度：高】【状態：決定済み：WikiPathwaysリポジトリのローカルcloneを利用】
- リフトオーバー操作に必要なファイルが何で、誰が用意するかが設計書に明示されていない。
- **確定した方針：**
  - GPMLファイル：WikiPathwaysのGitHubリポジトリ（`wikipathways/wikipathways-database`、`/pathways`以下）をローカルにcloneして利用する。パスウェイごとにディレクトリで管理され、`*.gpml`（パスウェイ情報本体）やアノテーションのtsvファイルが含まれる。cloneを最新状態に維持（pull）することで常に最新リソースを利用できる。
  - オルソログ変換テーブル：研究者が用意（必須）。ただしツールがオプションで作成支援することも検討中（A-1参照）
  - 発現データファイル：研究者が用意（任意）
  - 出力GPMLファイル：ツールが生成
- **決定の根拠：** WikiPathwaysのリポジトリが更新・版管理の正本として機能しており、APIや個別ダウンロードより安定かつ網羅的にアクセスできる。
- **残る設計上の問い：** cloneリポジトリのパスはツールの設定ファイルで指定するか、環境変数で渡すか。
- **補足：** ヒト対非モデル生物ではオルソログ対応表がないのが通常のため、表の「提供」だけでなく「作成」もツールのスコープに入りうる。プロジェクトにより最適な作成手法が異なるため、ツールでの作成はオプション機能として位置づける方向。
- 影響範囲：Level 1 Context図・スキーマ設計・入力バリデーション・設定ファイル仕様

### A-6. 入力パラメータの具体化・ID体系設定の仕様定義【重要度：高】【状態：議論中】
- Level 1の入力として何が必要か（ID体系、relation keyに使う属性、ツールパラメータ等）が曖昧。
- **背景：** ID体系はプロジェクト・生物種ごとに異なる可変パラメータであり設定として外部化が必要。仕様書ステップ3・5の注記（「今回はEnsemblのPIDだったため」「ミツバチではgeneIDで発現データと対応できなかったためtranscriptIDを使用」）がその根拠。
- **定義が必要な設定項目：**
  1. オルソログ変換テーブルの列マッピング（ヒト側・対象種側それぞれどの列がどのID体系か）
  2. GPMLノードのXREF_IDとして何を優先するか（geneID優先 / transcriptID許容）
  3. 発現テーブルのキー列のID体系（どの列をキーとして照合するか）
  4. **【PoC追加】GPMLノードのIdentifierタイプ：** geneID / Ensembl ID / EC番号（eccode）など複数タイプが存在し、タイプによって変換ルートが分岐する（A-8参照）。EC番号の場合はTOGOID等を経由する別ルートが必要（カイコPoC実績）。
- **判断が必要な問い：** 上記項目を設定ファイル（YAML等）として外部化するか、CLIの引数として渡すか。IdentifierタイプはGPML解析で自動判定できるか、それとも明示的に指定させるか。
- 影響範囲：Level 1 Context図・Level 3のパラメータ定義・C-3スキーマ設計（設定ファイル仕様の前段として扱う）・A-8（変換フロー分岐ダイアグラム）

### A-8. 変換フローの分岐ダイアグラム作成【重要度：高】【状態：未決定】
- PoCにより、変換フローが「NCBIのID同士で素直に対応できる場合」から「fanflow出力→tblastn補完→EC番号特殊ルート」まで複数の経路を持つことが判明した。
- **どこで分岐しどこが共通かを示すダイアグラム**が設計の前提整理に必要。特に以下の分岐点を整理する：
  1. **GPMLノードのIdentifierタイプ** — geneID / Ensembl ID / EC番号（eccode） / その他
  2. **対応表の入手経路** — 既存テーブルあり / fanflow生成 / NCBIから直接取得可能
  3. **BLAST手法** — 不要（対応表のみで完結） / blastp（タンパク質リファレンス） / tblastn（ヌクレオチドリファレンス）
  4. **未マップ遺伝子の扱い** — no hit（対応なし） / 1:N（パラログ統一） / 正常マップ
- **用途：** A-4（テーブル設計）・A-6（設定ファイル設計）・A-2（手動介入設計）・Level 3 Component設計の共通基盤として使う。
- **形式：** フローチャート（Mermaid）で条件分岐を表現する。`設計資料/仕様検討/` 内に作業版を置き、確定後に正本へ移動する。
- 影響範囲：A-1・A-2・A-4・A-6・Level 3設計全体

### A-7. オルソログ対応表が存在しない場合の扱い【重要度：中】【状態：議論中】
- **方針更新：** ヒト対非モデル生物では対応表が存在しないのが通常。「例外処理」ではなく「作成が必要な通常フロー」として設計し直す。
- ツール内でのオプション作成（RBH+等）を設けることで対応する方向。fanflowは外部ツールとして位置づけ。
- **残る問い：** 対応表が提供もされず作成オプションも使わない場合はエラーで終了か、警告付きで部分実行か。
- 影響範囲：Level 1 Context図・Level 3の分岐ポイント①（A-1の打ち合わせ後に確定）
